# 首输出前接管、失败亲和续租与停止原因

本说明定义 NewAPI 的候选准备、传输尝试和失败亲和处理边界；验证使用本地合成设施。

## 已复现并修复的缺口

真实 `Relay`、HTTP 客户端、SSE 解析器和选择器配合本地 HTTP/SQLite/Redis，数据库与内存缓存选路均复现：

| 合成请求路径 | 修复前 | 修复后 |
| --- | --- | --- |
| A 明确 HTTP 503 → B 无启用 Key → C 健康 | B 的准备失败被当作整轮无候选；C 未被调用 | 排除 B，继续选择 C，收到原生 `response.completed` |
| A 明确 HTTP 503 → B 写请求前连接拒绝 → C 健康 | B 继承 A 的“可能已接单”标记，被错误禁止继续接管 | 每次安全批准的新尝试拥有独立传输标记，C 正常完成 |
| 首次 Distribute 选中无启用 Key 的渠道，后面存在健康入口 | 进入 Relay 前直接失败 | 沿用同一候选跳过上限和请求排除，完整鉴权/分发链路正常接管 |
| 已有亲和命中 → response.created → response.failed，HTTP 仍为 200 | 剩余 40 秒的亲和绑定被误续到 60 秒 | 明确失败不续租，原绑定和值保留；真实成功和合法 incomplete 保持既有续租语义 |
| 指定渠道或明确配置亲和失败终止 → HTTP 503 | GPT 强制备用覆盖了显式终止约束 | 两个硬约束在强制备用分支同样生效；普通亲和仍允许安全的健康入口接管 |

首输出前的候选与传输修复不解释已经输出后发生的客户断流。亲和修复避免把已明确失败的流误记为成功续租，也不恢复已经中断的生成、不自动删除或迁移该失败请求的现有绑定。

## 本地实现

- 只对本地 `GetNextEnabledKey` 的精确 `channel:no_available_key` 准备失败继续选择；该候选在本次请求内持续排除。
- 空 Key 候选不消耗实际出站 `attempts`、`round_attempts` 或实际不同渠道数，另设最多 32 个候选跳过。继续受总 elapsed 与取消约束；到上限以 `candidate_limit_exhausted` 结束，不能宣称已经穷尽所有渠道。
- 初始 Distribute 和后续 Relay 使用共享 `RelayCandidateSkipLimit`、请求级候选排除和同一 elapsed 起点。首次已跳过 31 个候选，后续最多再跳过 1 个；不会重新获得 32 个名额。指定入口、模型权限、可用分组、auto_group 和显式亲和终止约束保持。
- `Relay` 只在原重试安全门已经批准下一次尝试后开启新的传输代数，清理本轮 accepted、连接、写请求和响应头阶段。全请求输出、收到的事件、工具、usage、状态归属及总时间预算均保留。
- HTTP trace 的接单标记以同一 atomic 代数校验；阶段和取消诊断通过代数 observer 隔离。旧请求迟到回调不能污染新尝试。
- 单次失败也记录最终 `relay_retry_final` 后台日志，字段只含渠道数字 ID、次数、不同渠道数、上限、耗时、固定停止原因与候选跳过数。增加 `upstream_outcome_unknown`，正确区分客户端取消、请求期限与输出已开始。日志不含密钥、请求正文或供应商名称。
- Relay 只在已知终态写入固定 `relay_final_outcome`。Distribute 仅排除明确 `failed` 的亲和续租；未标记的其他 handler 不被默认当作失败，合法 `incomplete` 不被错误升级为上游故障。

实际出站尝试包含连接失败；候选准备失败单独计数。MaxAttempts=2 时，A 的明确失败与健康备用的生成共占两次，连续两个空 Key 候选仍可被跳过。若第二次实际出站连接失败，不能绕过预算再发第三次。

## 保持的安全边界

- 收到 `response.created`、工具事件、下游输出后不重放；usage 已出现的失败也不盲目接管。
- 已写请求但结果未知、HTTP 200 后空流关闭、首事件等待失败不被解释为“上游未接单”。
- 精确请求错误、GPT 采样错误、state-owner 错误和 compact 的既有终止语义保持。
- 人工停用渠道不会被备用选择重新启用；候选准备失败不会改变持久渠道状态。
- 未把所有 400、502、`native_response_conversion_failed` 或 SSE 错误声明为安全重试；没有新增 CPA 错误作用域合同。
- 不修改持久渠道配置、路由权重或重试次数。

## 验证

- 修复前负对照：Relay 两种缺口 × 数据库/缓存共四个失败；初始空 Key × 三条路径 × 数据库/缓存共六个失败；亲和错误续租、指定渠道越界回退、显式亲和终止被覆盖均分别复现。
- 修复后：两种安全路径均到达不同健康候选并完成，MaxAttempts=2 连跳两个空 Key 后完成，全空候选到 32 有界停止。
- 完整 RequestId → TokenAuth → Distribute → Relay：首次空 Key、多个空 Key、初始与后续共同跳过均完成；模型权限、分组、auto_group、取消、elapsed、指定渠道和共享 32 上限负控通过。
- 亲和完整链路：HTTP 200 的明确失败不刷新 40 秒剩余 TTL、不改绑定；completed 与合法 incomplete 仍续到 60 秒。显式 SkipRetryOnFailure 阻止备用；关闭该选项后允许不同健康入口接管。
- 负控：已创建响应、工具事件、usage 错误、已写结果未知、空流、请求错误、state-owner、采样、取消、出站预算均不产生第二次不安全生成。
- 并发：旧代数 32 个并发 worker 的迟到标记/阶段回调被拒绝；新代数正常标记仍关闭重放门，已开始的阶段观察完成后再切换代数。
- 最终八个相关包全量测试、五包定向 race、五包 `go vet` 和 `git diff --check` 通过。

全部上游请求均为本地合成服务，不依赖外部模型生成。

## 诊断与覆盖边界

最终停止原因通过请求 ID 关联后台最终日志；既有逐次错误记录不会被事后改写。旧 CPA 的“已尝试全部”错误正文不由本补丁改写，也不能替代实际尝试数和停止原因。

初次分发和后续备用选路均由完整中间件与 Relay 集成回归覆盖。合成验证不证明外部认证池、供应商连接或其他生产错误已经恢复。
