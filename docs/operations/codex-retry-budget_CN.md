# GPT / Codex 外层补救预算

## 目标与范围

对原始模型名以 `gpt-` 开头、`POST /v1/chat/completions` 或 `POST /v1/responses` 的请求，使默认外层补救窗口与该请求已经建立的绝对截止时间一致。模型判定沿用 GPT 重试路径的原始模型命名空间，不依赖特定渠道 ID。

其他模型、Claude/Gemini 入口、图片、Realtime、Responses compact 等入口继续使用既有策略。此变更仅协调时间预算；不修改供应商、渠道选择、次数/轮次上限、错误分类或可重放条件。

## 原行为与问题

默认 `RELAY_RETRY_MAX_ELAPSED_SECONDS=180` 从初次选路起算。首事件和非流请求的总预算通常为 1200 秒。单次请求可以在第 180 秒以后返回一个允许恢复的失败，但外层随后的选路已被独立的 180 秒窗口阻止。

`MaxElapsed` 是进入下一次尝试/下一轮的门槛，不是强制终止进行中请求的定时器。因此单纯增加 attempts 不会恢复已被时间门槛停止的请求。

## 新行为

- 没有显式设置 `RELAY_RETRY_MAX_ELAPSED_SECONDS` 时，从 `RelayInfo` 读取已经固定的首事件或非流绝对截止时间，并取调用方 context deadline 中更早者。
- 将其换算为相对原始 `RelayRetryState.StartedAt` 的窗口。保留初次开始时间；不在重试/换渠道/下一轮重新起算。
- 如果没有任何有限请求截止时间，仍保留既有 180 秒默认窗口。
- 显式设置的 `RELAY_RETRY_MAX_ELAPSED_SECONDS` 保持原解析和限制行为；取消或调用方 deadline 仍由原有 context 检查停止请求。
- attempts、rounds、轮次退避、候选排除及错误可重试判定保持原逻辑。已输出、未知上游接受状态、精确状态持有错误等仍按现有保护停止，不因时间窗口更长而获得重放许可。

例如请求总预算 1200 秒、第一轮允许恢复的失败在累计 200 秒返回，默认情况下可以继续使用剩余约 1000 秒；不会从 200 秒再获得完整 1200 秒。

初始 middleware 的候选扫描继续使用既有候选预算。取得 `RelayInfo` 后、Relay 发起首次模型调用前，才对 GPT 文本路由应用此协调，以使用已经校验的原始模型和请求截止时间。

## 验证

本地合成测试包含：

- 实际 Relay、HTTP 传输及数据库/内存候选选择；把原始请求时钟回溯 179 秒，再让第一台本地模拟上游延迟 1.1 秒后返回 503。验证 Chat/Responses × 普通/流式 × 数据库/内存候选均能接管到第二台模拟上游。
- 用原版 controller 的 Go overlay 运行相同正例，验证旧实现只尝试第一台后在 180 秒门槛停止，负对照必须失败。
- 非 GPT、显式 180 秒设置、最大 attempts、调用方取消、已发送工具事件、未知请求接受状态、状态持有错误保持停止。
- 单元测试验证绝对截止不随下一轮刷新、较早 context deadline 生效、过期截止不能恢复、显式设置与其他入口保持不变。

所有上游、凭据、消息和数据库均为本地合成；本地通过不是 CI、部署或生产恢复证明。
